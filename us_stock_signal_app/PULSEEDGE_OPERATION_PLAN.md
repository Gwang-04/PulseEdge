# PulseEdge 운영/출시 구조 계획

작성일: 2026-09-15

PulseEdge는 미국 주식의 단기 스윙부터 몇 개월 보유 관점을 돕는 투자 참고용 앱이다. 지금 단계의 핵심은 자동매매가 아니라 `관심종목 감시`, `보유종목 관리`, `신호 로그`, `알림`이다.

이 문서는 실제 서비스로 옮길 때 서버, API 키, 로그인, 푸시, 데이터 저장, 법적 고지를 어떤 순서로 붙일지 정리한 운영 기준이다. 법률 자문이 아니며, 유료 출시 전에는 금융/개인정보/앱스토어 심사 기준을 전문가와 별도 검토해야 한다.

## 1. 현재 결론

- 시작은 `무료 PWA + 게스트/로컬 저장`으로 간다.
- 로그인 전 단계에서는 브라우저별 익명 ID로 게스트 설정을 분리한다.
- 종목 상세 차트는 TradingView 위젯으로 표시한다.
- 현재 Alpaca 연결과 신호 엔진은 개인용 버전으로 보존한다.
- 공개 버전의 분석 데이터 제공사는 재배포/상업 이용 범위를 확인한 뒤 확정한다.
- 사용자는 시장 데이터 API Key를 입력하지 않는다.
- 시장 데이터 키가 필요한 경우 운영자 서버의 환경변수에만 둔다.
- 앱은 매수/매도 주문을 실행하지 않는다.
- 앱은 초단타, 분봉/틱 단위 매매, 실시간 주문 판단용이 아니라 일봉/주봉 기반 스윙 점검용으로 둔다.
- 화면 표현은 `매수`, `매도`, `무조건`, `수익 보장`보다 `진입검토`, `방어검토`, `수익보호`, `대기`를 쓴다.
- 백테스트는 마케팅 핵심 문구가 아니라 내부 검증과 보고서 기록으로 둔다.
- 로그인은 처음부터 필수로 넣지 않고, 클라우드 저장/실제 푸시/유료화 단계에서 추가한다.

## 2. 5달러급 DigitalOcean 서버 판단

5달러급 소형 서버는 개인 사용, 지인 테스트, 소규모 베타에는 충분히 쓸 수 있다. 다만 공개 앱으로 사용자가 늘어나면 `매 사용자 x 관심종목 x 새로고침` 구조 때문에 데이터 요청량과 서버 부하가 먼저 문제가 된다.

가능한 초기 구조:

```text
사용자 브라우저/PWA
  -> PulseEdge 웹 서버
  -> 서버 캐시
  -> Alpaca/CBOE 데이터 요청, VIX 실패 시 FRED 대체
  -> 신호 엔진 계산
  -> 화면/로그/브라우저 알림
```

초기 서버에서 꼭 지킬 것:

- `/api/analyze` 요청을 그대로 데이터 제공사에 매번 흘리지 않고 서버 캐시를 둔다.
- 관심종목 전체 분석은 종목별 데이터를 병렬로 가져오되, 소형 서버와 무료 API를 고려해 동시 작업 수를 제한한다.
- 같은 티커의 일봉 데이터는 최소 몇 분 단위로 재사용한다.
- 캐시 적중률, 외부 요청 수, Alpaca 429 횟수를 앱에서 확인할 수 있게 한다.
- 자동 새로고침은 최소 15분으로 제한한다.
- VIX는 CBOE 공식 일봉 종가를 우선 사용하고 실패 시 FRED로 전환하며, 서버 메모리에서 1시간 재사용한다.
- 관심종목 최대 개수와 새로고침 주기를 제한한다.
- API 키는 `.env` 또는 서버 환경변수에만 저장하고 클라이언트로 내려보내지 않는다.
- HTTPS 도메인을 붙이고, 운영 포트는 방화벽으로 정리한다.

소형 서버로 어려워지는 시점:

- 동시 사용자가 많아져 같은 시간에 분석 요청이 몰릴 때
- 사용자별 관심종목이 수십 개 이상으로 늘 때
- 1분/5분봉 같은 잦은 데이터가 필요해질 때
- 실제 모바일 푸시를 서버가 주기적으로 계산해 보내야 할 때
- 로그인, 결제, 사용자별 히스토리 저장이 붙을 때

그때는 `웹 서버`, `스케줄러/워커`, `DB`, `캐시`를 분리하는 쪽으로 간다.

## 3. API 키와 데이터 정책

사용자 API Key 입력은 하지 않는다.

이유:

- 사용자가 키를 발급받는 과정이 어렵고 이탈이 커진다.
- 사용자의 민감한 키를 저장/보호해야 하는 책임이 생긴다.
- 데이터 라이선스와 상업 이용 설명이 복잡해진다.
- 앱이 초보자용이라는 제품 방향과 맞지 않는다.

운영 방식:

- TradingView Advanced Chart 위젯은 사용자에게 차트를 보여주는 용도로만 사용한다.
- TradingView 위젯 내부 가격과 보조지표 값을 PulseEdge 서버로 추출하거나 신호 계산 데이터로 재사용하지 않는다.
- TradingView 출처 링크와 브랜드 표시는 제거하지 않는다.
- 개인용 Alpaca 키는 서버 환경변수 `APCA_API_KEY_ID`, `APCA_API_SECRET_KEY`에 저장한다.
- 로컬 테스트는 `.env.example`을 `.env`로 복사해서 쓰고, 실제 `.env`는 저장소에 올리지 않는다.
- 서버는 `APCA_API_KEY_ID`, `APCA_API_SECRET_KEY`를 우선 읽고, 호환용으로 `ALPACA_API_KEY_ID`, `ALPACA_API_SECRET_KEY`도 읽는다.
- 앱 화면에는 `데이터 서버 준비됨`, `IEX 단일 거래소`, `Delayed SIP 지연`, `VIX 일봉 종가` 같은 데이터 기준만 보여준다.
- 공개 출시 전에는 PulseEdge 점수와 신호에 사용할 원천 데이터 제공사의 재배포/파생 데이터/상업 이용 가능 범위를 별도로 확인한다.
- 제공사 계약이 정해지기 전에는 Alpaca 기반 분석을 개인용 또는 비공개 테스트 범위로 유지한다.
- 무료 플랜에서는 데이터 한계가 있으므로 앱 내 고지와 오류 표시를 유지한다.

## 4. 로그인 도입 기준

초기 무료 테스트는 로그인 없이 간다. 로그인은 제품을 무겁게 만들고, 개인정보 처리와 계정 삭제 책임도 같이 생긴다.

| 기능 | 로그인 필요성 | 판단 |
| --- | --- | --- |
| 한 기기에서 무료 PWA 사용 | 낮음 | 로컬 저장으로 충분 |
| 관심종목/보유종목 클라우드 저장 | 높음 | 사용자 식별 필요 |
| 폰/PC 동기화 | 높음 | 로그인 필요 |
| 실제 모바일 푸시 | 높음 | 기기 토큰과 사용자 매핑 필요 |
| 유료 구독 | 높음 | 결제/권한/환불 관리 필요 |
| 계정별 신호 히스토리 | 높음 | DB와 계정 필요 |

권장 순서:

1. 게스트 모드로 앱 완성도 확인
2. Supabase 이메일/Google 로그인 설정
3. 게스트 데이터를 로그인 계정으로 한 번 병합
4. 계정·데이터 삭제 구현 후 폰/PC 동기화 실전 점검
5. 푸시 구독 정보 저장
6. 유료 기능과 결제 연결

현재 로그인 기반 구현:

- Supabase 설정이 없으면 게스트 모드를 유지한다.
- 브라우저는 Supabase 세션을 보관하고 PulseEdge API 요청에 access token을 보낸다.
- 서버는 Supabase Auth 사용자 조회 API로 토큰을 검증하고, 검증된 외부 사용자 ID만 SQLite 계정과 연결한다.
- 첫 연결은 게스트 데이터를 계정에 복사한다. 다른 기기의 게스트 데이터는 기존 계정 설정을 덮지 않고 관심종목과 새 보유종목만 한 번 합친다.
- PulseEdge DB에는 비밀번호, access token, refresh token을 저장하지 않는다.
- Settings에서 로그인 이메일 재입력 후 Supabase 계정, SQLite 계정·연결 게스트 데이터, 브라우저 로컬 데이터를 함께 삭제한다.
- 삭제된 인증 식별자는 표식으로 남겨 만료 전 access token이 계정 데이터를 다시 만들지 못하게 한다.
- 영구 삭제는 서버 전용 `SUPABASE_SECRET_KEY`가 설정된 경우에만 활성화한다. 기존 `SUPABASE_SERVICE_ROLE_KEY`는 호환용으로만 지원한다.

## 5. 알림 구조

현재 앱:

- 브라우저 알림 권한이 허용된 경우에만 `즉시` 신호를 알림으로 띄운다.
- 앱을 처음 열어 분석한 신호는 푸시 없이 로그에만 남긴다.
- 같은 `관점 + 티커 + 신호 + 거래일`은 하루에 한 번만 기록한다.
- `요약` 신호는 Home의 `오늘의 핵심` 박스와 Signals 로그에서 확인한다.

나중에 실제 모바일 푸시로 가는 구조:

```text
서버 스케줄러
  -> 사용자별 관심종목/보유종목 조회
  -> 데이터 캐시 확인
  -> 신호 계산
  -> 중복 알림 체크
  -> 푸시 발송
  -> 알림 로그 저장
```

PWA 푸시를 선택하면 서비스워커 푸시 구독과 VAPID 키가 필요하다. Expo/React Native 앱으로 가면 APNs/FCM 또는 Expo Push Token 관리가 필요하다. 둘 다 사용자별 기기 토큰 저장이 필요하므로 로그인 또는 최소한의 익명 계정 구조가 필요하다.

## 6. 개인정보와 저장 데이터

초기 로컬/게스트 모드에서 저장되는 정보:

- 관심종목
- 보유 여부
- 평단가
- 수량
- 매수일
- 실적일
- 메모
- 알림 설정
- 투자 유의 동의 버전/시간
- 신호 로그

현재 구현 기준:

- 브라우저는 `localStorage`에 `pulseedgeClientId`를 저장한다.
- 서버 API 요청에는 `X-PulseEdge-Client-Id` 헤더가 붙는다.
- 서버는 사용자별 설정을 `user_data/pulseedge.sqlite3`의 사용자 ID별 행으로 저장한다.
- 기존 `user_data/guests/<client_id>.json`은 최초 접근 때 자동 이전하고 백업으로 남긴다.
- `config.json`은 기본 템플릿/로컬 기본값 역할로 둔다.
- `user_data/`는 개인 설정이므로 저장소에 올리지 않는다.
- 운영 서버에서는 `pulseedge.sqlite3`를 정기 백업하고, 실행 중 백업은 SQLite backup API 또는 서버 스냅샷을 사용한다.
- 공개 배포 전에는 개인 보유종목이 들어간 `config.json`을 기본값으로 그대로 쓰지 않는다.

로그인 운영에서 계속 준비해야 할 것:

- 개인정보 처리방침
- 이용약관
- 계정 삭제 기능 운영 점검
- 고객지원 기반 데이터 삭제 요청 절차
- 알림 수신 동의/철회
- 결제/환불 정책
- 서버 로그 보관 기간
- DB 백업과 복구 정책

민감도 기준:

- 관심종목 자체는 낮은 민감도처럼 보여도 투자 성향을 추정할 수 있다.
- 평단가, 수량, 손익, 메모는 투자 보유 정보이므로 더 조심해서 다룬다.
- 공개 앱에서는 HTTPS, 인증, 접근 제한, 백업 암호화, 관리자 접근 로그가 필요하다.

## 7. 법적/표현 가드레일

PulseEdge는 투자 참고용 도구로 유지한다. 공식 자료 기준으로도, 보상을 받고 증권에 관한 조언이나 분석을 정기적으로 제공하는 경우 투자자문 규제 이슈가 생길 수 있다. 미국 SEC/Investor.gov는 투자 조언, 증권 분석/보고서, 보상, 정기적 영업성을 중요한 요소로 설명한다.

한국 사용자를 대상으로 유료 운영을 한다면 유사투자자문업/투자자문업 해당 여부를 별도 검토한다. 금융위원회 자료도 불특정 다수에게 개별성 없는 조언만 가능한 경우와 1:1 투자자문 가능 범위를 구분하고, 손실 보전이나 이익 보장 표현을 금지 방향으로 안내한다.

피해야 할 것:

- `지금 매수`, `지금 매도`, `무조건 진입`, `확정 수익`
- 특정 사용자 상황에 맞춘 1:1 포트폴리오 비중 추천
- 손실 보전 또는 수익 보장 표현
- 백테스트 수익률을 미래 성과처럼 말하기
- 자동 주문 실행 또는 계좌 운용 대행처럼 보이는 흐름
- 유료 회원에게 개별 종목/가격을 1:1로 지시하는 운영

앱 안에 유지할 것:

- 첫 실행 투자 유의 동의
- Settings의 접이식 위험 고지
- 데이터 기준/지연/오류 가능성 고지
- 초단타/실시간 주문 판단용이 아니라는 고지
- 신호는 검토 우선순위라는 표현
- 주문 전 사용자가 직접 차트, 공시, 뉴스, 리스크를 확인해야 한다는 안내

## 8. 출시 단계

### Phase A: 개인 PWA

- 로컬/개인 서버에서 사용
- Alpaca 키는 개인 서버 `.env`
- 로그인 없음
- 브라우저 알림만 사용
- 목적: 기능 감각, 점수표, UX 검증

### Phase B: 소규모 베타

- DigitalOcean 서버 배포
- HTTPS 도메인 연결
- 서버 캐시와 제한된 병렬 분석 적용
- 간단한 상태 페이지/헬스체크
- 사용자 API 키 입력 없음
- 가입 없이 테스트 링크 공유 가능

### Phase C: 계정/동기화

- 로그인 및 사용자별 관심종목/보유종목 DB 저장 완료
- 계정 삭제/데이터 삭제 구현 완료, 실제 Supabase 키 환경에서 최종 점검 필요
- 서버 로그 정책 정리
- 개인정보 처리방침과 이용약관 준비

### Phase D: 실제 푸시/앱화

- PWA Push 또는 Expo/React Native 선택
- 사용자별 기기 토큰 저장
