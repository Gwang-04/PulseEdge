# PulseEdge 현재 버전 보고서

작성일: 2026-09-03  
업데이트: 2026-09-29  
기준 앱: PulseEdge 로컬 프로토타입 v0.1  
데이터 기준: Alpaca Free / IEX, CBOE VIX 공식 일봉 우선·FRED VIXCLS 예비  
문서 목적: 지금까지 정한 기능, 화면, 점수 기준, 백테스트 룰, 남은 과제를 한 곳에 기록한다.

## 1. 한 줄 요약

PulseEdge는 미국 주식을 단타가 아니라 단기 스윙부터 몇 개월 보유 관점으로 감시하는 모바일 우선 PWA다. 자동 주문은 하지 않고, 관심종목은 진입 검토 관점으로, 보유종목은 수익보호/방어/관리 관점으로 분석해서 알림과 점수를 제공한다.

투자 판단은 사용자가 최종 결정한다. 앱의 신호는 매수/매도 명령이 아니라 `검토`, `후보`, `관리`, `축소검토`를 위한 참고 지표다.

## 2. 현재 방향

- 앱 이름: `PulseEdge`
- 컨셉: US Swing Signal
- 주 사용 기간: 며칠짜리 초단타보다 단기 스윙, 몇 주에서 몇 개월 보유
- 초기 형태: 웹 + 모바일 PWA
- 나중 방향: 로그인/클라우드 저장/푸시 알림/모바일 앱 전환 가능
- 실거래 주문: 현재 버전에서는 제외
- 무료 데이터 우선: Alpaca Basic 무료 IEX, CBOE VIX 공식 일봉과 FRED 예비 소스
- 화면 원칙: 매일 보는 앱은 최소화한다. 새 기능은 바로 붙이지 않고 개선 후보로 기록한 뒤 필요성이 확인되면 추가한다.
- 현재 하단 탭: `Home`, `Watch`, `Hold`, `Signals`, `Settings`

## 5. 구현 완료 기능

### 5.1 앱 구조

- Python 로컬 서버
- 정적 HTML/CSS/JS 프론트엔드
- 모바일 우선 다크모드 UI
- PWA 매니페스트와 서비스워커
- Android/iOS 홈 화면 아이콘용 PNG 아이콘
- 기본 설정용 `config.json`
- 사용자별 SQLite 저장소 `user_data/pulseedge.sqlite3`
- 서버/운영자용 API 키 저장 `.env`
- 관심종목/보유종목/알림 설정 저장
- 실제 Alpaca 데이터와 데모 데이터 전환

### 5.2 주요 화면

| 화면 | 역할 |
| --- | --- |
| Home | 시장 상태, VIX, 오늘 볼 종목 TOP, 핵심 기회/주의 요약 |
| Watch | 관심종목을 미보유라고 가정하고 진입점수 기준으로 표시, 빠른 추가/삭제 지원 |

| Settings | 데이터 서버 상태, 점수 기준표, 관심종목, 보유종목, 알림, 용어 설명 관리 |

백테스트 화면은 사용자용 하단 탭에서 제외했다. 백테스트 엔진과 API는 내부 검증/보고서 기록용으로 유지한다.

### 5.3 차트 기능

- 종목 카드를 누르면 상세 차트가 열린다.
- Watch/Hold 카드에는 차트를 넣지 않아 모바일에서 많은 종목을 빠르게 훑을 수 있게 했다.
- 일봉/주봉 전환 가능
- 3개월/6개월/1년/전체 범위 전환 가능
- 휠/터치패드/핀치 확대 축소
- 드래그 이동
- 캔들, 거래량, RSI 표시
- 20/60/120일 이동평균선 표시
- 볼린저밴드 켜기/끄기
- 일목균형표 구름 켜기/끄기
- 사용자가 직접 추세선 그리기
- 자동 지지선/저항선 표시
- 보유종목은 평단, 손절선, 트레일링선 표시
- 보유종목 카드와 상세 보유 정보에서 `방어선`, `위험선`, `수익보호`를 분리 표시
- 신호 로그는 날짜별 최신순 그룹, 필터 칩, 레벨/전달방식 배지로 정리

## 6. 관심종목과 보유종목 처리 원칙

### 6.1 Watch 화면

Watch는 종목을 보유하고 있어도 미보유라고 가정한다. 이유는 관심목록에서는 “지금 신규 진입해도 되는 자리인가?”를 보고 싶기 때문이다.

Watch 기준:

- 점수 이름: `진입점수`
- 기본점수: 50점
- 100점에 가까울수록 진입 검토 근거가 강함
- 0점에 가까울수록 신규 진입을 피해야 함
- 보유 여부와 평단은 반영하지 않음
- 정상이라는 표현 대신 `대기`를 사용
- Home의 `오늘 볼 종목`은 이 Watch 기준 점수에 RSI, 거래량, 지지선/저항선 거리, 시장 리스크를 더해 상위 3개를 압축 표시
- Home의 `진입 관찰`도 Watch 점수 단계 이름을 사용해 Watch 카드와 표현을 맞춤

### 6.2 Hold 화면

Hold는 실제 보유 기준으로 본다. 평단, 수익률, 손절선, 매수일 이후 고점, 트레일링, 보유 이후 지지/저항선을 반영한다.

Hold 기준:

- 점수 이름: `관리강도`
- 기본점수: 50점
- 높을수록 관리/수익보호/방어 검토 필요
- 낮을수록 안정 보유
- 80점 이상은 관리강화 구간
- 90점 이상은 강한관리 구간
- 관리강도 내부는 `방어`, `수익보호`, `이벤트`로 나눠 표시
- 최종 관리강도는 방어와 수익보호 중 더 급한 쪽에 이벤트 점수를 일부 더해 계산

## 7. 점수 계산 방식

점수는 단순히 하나의 신호로 정하지 않는다. 이벤트 신호와 현재 상태 점수를 같이 합산한다.

```text
최종점수 = 50 + 상태점수 + 이벤트신호점수
최종점수 = 0~100 사이로 제한
레벨별 최소점수와 최대점수 보정 적용
```

구성:

- 상태점수: RSI 구간, 거래량 구간, 이평선 위/아래 개수, 이평선 이격, 볼린저 위치, 일목 위치, 지지/저항 근접도, 보유 손익/방어선
- 이벤트 신호점수: RSI 과매도, RSI 회복, 거래량 급증, 이평선 회복/이탈, 신고가/신저가, 갭, 볼린저/일목 이벤트, 방어/수익보호/실적/VIX
- 점수 근거는 절댓값이 큰 순서대로 최대 6개까지 UI에 표시

보유종목은 최종 점수와 함께 하위 점수를 표시한다.

| 하위 점수 | 역할 |
| --- | --- |
| 방어 | 손실률, 고정손절, S1 지지선 이탈, 60/120일선 이탈, 하락 거래량 |
| 수익보호 | +10/+20/+30 수익 구간, 이평선 과열 이격, RSI 과열, 트레일링, 저항선 근접 |
| 이벤트 | VIX, 시장 리스크, 실적 일정 |

최종 관리강도:

```text
관리강도 = max(방어점수, 수익보호점수) + 이벤트점수 일부
```

## 8. 진입점수 단계표

미보유 또는 Watch 화면 기준이다.

| 점수 | 단계 | 의미 |
| --- | --- | --- |
| 85~100 | 진입검토 | 여러 조건이 겹친 강한 진입 검토 구간 |
| 70~84 | 자리검토 | 점수는 좋지만 강한 이벤트 신호가 없으면 차트 자리 확인 필요 |
| 62~69 | 반등체크 | 반등이 확정됐다는 뜻이 아니라 추가 확인 필요 |
| 55~61 | 관찰 | 관찰할 만한 조건 일부 발생 |
| 45~54 | 대기 | 뚜렷한 매수 근거 없음 |
| 30~44 | 주의 | 신규 진입 신중 |
| 0~29 | 진입금지 | 신규 진입 피하는 구간 |

단, `기회후보` 또는 `돌파후보` 같은 강한 이벤트 신호가 붙은 70점대는 `진입검토`로 표시한다.

진입점수 보정:

| 알림 레벨 | 최소점수 |
| --- | --- |
| 관심 | 55 |
| 공포관심 | 60 |
| 반등후보 | 62 |
| 기회후보 | 70 |
| 돌파후보 | 74 |
| 기본 | 50 |

| 알림 레벨 | 최대점수 |
| --- | --- |
| 주의 | 44 |
| 위험 | 25 |

즉, 미보유 종목에서 `주의`나 `위험`이 뜨면 다른 상태점수가 좋아도 점수 상단을 제한한다.

## 9. 관리강도 단계표

보유종목 또는 Hold 화면 기준이다.

| 점수 | 단계 | 의미 |
| --- | --- | --- |
| 90~100 | 강한관리 | 과열, 리스크, 트레일링 훼손 등 강한 관리 필요 |
| 80~89 | 관리강화 | 수익 보호나 위험 회피를 더 자주 확인할 구간 |
| 70~79 | 점검필요 | 수익 보호나 방어 기준을 점검할 구간 |
| 60~69 | 집중관리 | 손절선, 이평선, 거래량, 변동성 점검 필요 |
| 50~59 | 관찰 | 평소보다 약간 더 볼 필요 있음 |
| 30~49 | 안정보유 | 특별한 위험이 적은 안정 보유 구간 |
| 0~29 | 매우안정 | 관리 압력이 낮은 구간 |

관리강도 보정:

| 알림 레벨 | 최소점수 |
| --- | --- |
| 수익관리 | 55 |
| 주의 | 60 |
| 수익보호검토 | 70 |
| 방어검토 | 75 |
| 위험 | 85 |

보유종목은 최대점수 제한이 없다. 위험 신호가 여러 개 겹치면 100점까지 올라갈 수 있다.

Settings에는 위 진입점수/관리강도 단계표를 접이식 `점수 기준표`로 표시한다. 앱 화면에서는 `진입검토`, `방어검토`, `강한관리` 같은 표현이 주문 지시가 아니라 검토 우선순위임을 함께 안내한다.

## 16. 자동 지지선/저항선 기준

### 16.1 미보유 기준

- 최근 180일 기준
- 3봉 좌우 피벗 고점/저점 추출
- 60일/120일 고점과 저점 추가
- 가까운 지지선 3개, 저항선 3개 표시

### 16.2 보유 기준

보유종목은 매수일 이후 기준이 우선이다.

- 매수일 이후 피벗 고점/저점
- 매수일 이후 최고가/최저가
- 매수일 당일 고가/저가
- 평단가
- 60일/120일 고점/저점

따라서 보유로 넘어간 종목은 일반 최근 180일 지지/저항이 아니라, “내가 산 뒤 생긴 방어선과 수익권 저항”을 더 중요하게 본다.

### 16.3 지지/저항 점수

| 조건 | 미보유 점수 | 보유 점수 |
| --- | ---: | ---: |
| 지지선 1% 이내 | +9 | +8 |
| 지지선 2.5% 이내 | +6 | +5 |
| 지지선 5% 이내 | +3 | +2 |
| 저항선 1.5% 이내 | -10 | +7 |
| 저항선 3% 이내 | -6 | +4 |
| 저항선 5% 이내 | -3 | +2 |
| 미보유에서 저항선 10% 이상 위 | +3 | - |

최종 지지/저항 상태점수는 -12점부터 +12점 사이로 제한한다.

### 16.4 선 강도

- 같은 가격대에 여러 번 닿을수록 강함
- 최근 20봉 이내 터치면 가산
- 최근 60봉 이내 터치면 약한 가산
- 여러 출처가 겹치면 가산
- 강도는 1~5로 표시
- 가격대 클러스터 허용 오차는 약 1.4%

## 17. 보유종목 관리 기준

현재 손절은 고정손절 하나만 보지 않는다. 고정손절은 최후의 방어선이고, 실제 스윙 관리는 `매수일 이후 구조`를 중심으로 본다.

화면 표시 기준은 다음처럼 분리한다.

| 표시 | 의미 |
| --- | --- |
| 방어선 | 매수일 이후 S1 지지선, 60일선, 120일선 중 현재가 아래에서 가장 가까운 구조선 |
| 위험선 | 설정 손절률로 계산한 최후 손절 기준가 |
| 수익보호 | 수익 중일 때 매수일 이후 최고 종가 기준 트레일링 기준가 |

구조선 이탈 신호가 이미 발생한 경우에는 `방어선` 칸에 현재 아래 지지선보다 최근 깨진 구조선을 우선 표시한다. 이때 표시는 `이탈선 · 이탈 n%`가 되어 `구조방어검토` 사유가 바로 보이게 한다.

| 구조 기준 | 판단 |
| --- | --- |
| S1 지지선 3% 이내 + 하락 압력 | 방어선확인 |
| S1 지지선 종가 1% 이상 이탈 | 구조방어검토 |
| S1 이탈 + 하락 거래량 1.5배 이상 | 위험축소검토 |
| S1 이탈 + 60일선 이탈 | 위험축소검토 |
| 60일선 2거래일 연속 이탈 | 구조방어검토 |
| 120일선 이탈 | 강한 방어 점검 |

### 17.1 손익 상태점수

| 평단 대비 수익률 | 상태점수 |
| --- | ---: |
| -10% 이하 | +18 |
| -7% 이하 | +12 |
| -5% 이하 | +8 |
| 0% 미만 | +3 |
| +5% 이상 | +2 |
| +10% 이상 | +4 |
| +20% 이상 | +6 |
| +30% 이상 | +8 |

주의: 이 표는 상태점수다. 별도로 `PROFIT_30` 같은 이벤트 신호점수가 붙을 수 있다. 현재 +30% 수익권에서는 수익 이벤트 +8점과 수익률 상태 +8점이 함께 반영될 수 있다.

### 17.2 손절선 버퍼

손절선은 `평단 * (1 + 손절률)`로 계산한다.

| 손절선까지 남은 거리 | 점수 |
| --- | ---: |
| 이미 손절선 아래 | +22 |
| 3% 이내 | +14 |
| 6% 이내 | +8 |
| 10% 이상 여유 | -3 |
| 15% 이상 여유 | -5 |
| 25% 이상 여유 | -8 |

### 17.3 트레일링 버퍼

트레일링 기준가는 `매수일 이후 최고 종가 * (1 + 트레일링률)`로 계산한다.

| 트레일링선까지 남은 거리 | 점수 |
| --- | ---: |
| 이미 트레일링선 아래 | +18 |
| 3% 이내 | +9 |
| 6% 이내 | +4 |
| 8% 이상 여유 | -2 |
| 10% 이상 여유 | -3 |
| 15% 이상 여유 | -5 |

위험선/트레일링 버퍼 상태점수는 합산 후 -16점부터 +24점 사이로 제한한다.

## 18. 시장 필터와 VIX 기준

### 18.1 SPY/QQQ 시장 필터

- SPY와 QQQ가 모두 120일선 위면 `리스크온`
- 둘 다 120일선 아래면 `리스크오프`
- 일부만 아래면 주의 상태로 본다.
- 홈에는 `SPY 120일선 +4.54%`처럼 현재가가 120일선 대비 몇 퍼센트 위/아래인지 `+/-`로 표시한다.

### 18.2 VIX 기준

| 조건 | 레벨 | 의미 |
| --- | --- | --- |
| VIX 20 이상 | 주의 | 변동성 주의 |
| VIX 25 이상 | 위험 | 공포 구간 |
| VIX 30 이상 | 위험 | 극단 공포 |
| 5거래일 +20% 이상 | 위험 | 공포 급등 |
| 5거래일 -12% 이하 | 관심 | 공포 진정 |

VIX가 공포 또는 급등 구간이면:

- 보유종목에 `VIX_POSITION_RISK`가 붙을 수 있다.
- 미보유 기회후보/돌파후보는 `MARKET_FILTER_DOWNGRADE`로 낮아질 수 있다.
- VIX는 현재 일봉 종가라서 장중 실시간 변화와는 차이가 있을 수 있다.

## 19. 백테스트 기능

### 19.1 백테스트 목적

현재 점수 룰이 실제로 쓸 만한지 보기 위한 첫 검증 도구다. “진입점수가 특정 기준 이상이었던 날”을 과거에서 찾아 다음 거래일 시가로 진입했다고 가정한다.

### 19.2 기본 입력값

| 항목 | 현재 기본값 |
| --- | --- |
| 종목 | 관심목록에서 선택 |

| 조회 기간 | 252거래일 |
| 쿨다운 | 10거래일 |

### 19.3 90일 보유형 룰

현재 추천 기본 룰이다. 미국주식 관심종목은 우상향 구간에서 너무 빨리 팔면 수익을 줄일 수 있어서, 먼저 “신호가 뜬 자리를 그냥 보유했을 때 어땠는지”를 보는 기준으로 둔다.

| 항목 | 값 |
| --- | --- |
| 진입 | 신호 다음 거래일 시가 |
| 중간 손절 | 없음 |
| 중간 익절 | 없음 |
| 트레일링 | 없음 |
| 최대 보유 | 90거래일 |
| 청산 | 90거래일째 종가 |

### 19.4 수익형 룰

수익형 룰은 비교용이다. 평균수익률을 더 보려는 방향에 맞춰 균형형보다 느슨한 손절/긴 보유/높은 목표를 사용하지만, 최근 테스트에서는 90일 보유형보다 수익을 빨리 잘라낸 경향이 있었다.

| 항목 | 값 |
| --- | --- |
| 진입 | 신호 다음 거래일 시가 |
| 손절 | -8% |
| 1차 익절 | +15% 도달 시 25% 매도 |
| 2차 익절 | +25% 도달 시 25% 매도 |
| 트레일링 | 1차 익절 후 남은 물량 고점 대비 -10% |
| 최대 보유 | 90거래일 |

### 19.5 수익형+구조손절 룰

수익형 룰에 구조손절을 추가한 방어형 비교 옵션이다. 평균수익률을 무조건 올리는 목적보다는, 고정 -8% 손절까지 기다리기 전에 구조가 깨진 거래를 먼저 줄여 MDD를 낮추는 성격이다.

| 항목 | 값 |
| --- | --- |
| 진입 | 신호 다음 거래일 시가 |
| 기본 룰 | 수익형과 동일 |
| 구조손절 1 | S1 지지선 1% 이상 종가 이탈 + -6% 손실 확인 |
| 구조손절 2 | 60일선 2거래일 연속 종가 이탈 + -6% 손실 확인 |
| 청산 | 구조손절 신호 다음 거래일 시가 |

### 19.6 균형형 룰

| 항목 | 값 |
| --- | --- |
| 진입 | 신호 다음 거래일 시가 |
| 손절 | -7% |
| 1차 익절 | +12% 도달 시 30% 매도 |
| 2차 익절 | +20% 도달 시 30% 매도 |
| 트레일링 | 1차 익절 후 남은 물량 고점 대비 -8% |
| 최대 보유 | 60거래일 |

### 19.9 MDD 의미

MDD는 수익률이 아니라 `진입 후 가장 크게 밀린 폭`이다. 예를 들어 평균 MDD -4.62%는 해당 룰의 거래들이 평균적으로 진입 후 한때 -4.62%까지 흔들렸다는 뜻이다.

### 19.10 현재 백테스트 한계

- 수수료/슬리피지 미반영
- 종목 하나씩만 테스트
- 포트폴리오 단위 자금관리 미반영
- 과거 SPY/QQQ/VIX 시장 필터 완전 재현은 아직 제외
- 같은 날 고가/저가 순서를 알 수 없으므로 보수적으로 손절을 먼저 체크
- 트레일링은 1차 익절 다음 거래일부터 작동
- 90일 보유형과 90D 고정수익 비교에는 이후 90거래일 결과가 필요하므로 최근 신호 일부는 제외될 수 있음
- 표본 수가 적으면 결과 신뢰도가 낮음

## 20. 알림 설정 원칙

각 신호는 설정에서 다음 모드 중 하나로 고를 수 있다.

| 모드 | 의미 |
| --- | --- |
| 즉시 | 바로 알림 대상으로 표시 |
| 요약 | 요약 알림 대상 |
| 기록 | 기록만 남김 |
| 끔 | 신호 계산/표시에서 제외 |

새 신호는 `관점 + 티커 + 신호 종류 + 거래일` 기준으로 구분한다. 관점은 `관심`, `보유`, `시장` 세 가지이며, 같은 종목이라도 관심 기준 진입 신호와 보유 기준 방어 신호는 서로 다른 신호로 본다.

같은 신호는 같은 거래일에 한 번만 기록/알림한다. 기존 로컬 저장소의 예전 키(`티커:신호:오늘`)도 읽어서 새 구조로 자연스럽게 옮긴다.

앱을 처음 열었을 때 분석된 신호는 로그에만 남기고 브라우저 푸시는 보내지 않는다. 이후 새로 발생한 `즉시` 신호만 푸시 대상으로 보며, 처리 우선순위는 보유 위험/수익관리, 시장 신호, 관심 진입 신호 순서다.

현재 추천 기본값은 `조용하지만 중요한 건 놓치지 않는 모드`다. 보유 방어, 구조 이탈, `PROFIT_30`, `TRAILING_STOP_REVIEW`, 보유 RSI 과열 식음, 실적 하루 전/당일, 시장 리스크오프, VIX 공포/극단공포는 즉시로 둔다.

매수 후보성 신호와 과민할 수 있는 보조 신호는 요약으로 둔다. 예시는 `RSI_RECOVERY`, `BEARISH_VOLUME_SPIKE`, `MA60/MA120_BREAKDOWN`, `DEAD_CROSS_20_60`, `LOW_60/LOW_120_BREAKDOWN`, `VOLUME_CONFIRMED_BREAKOUT`, `GAP_DOWN`, `PROFIT_20`, `TRAILING_STOP_WARNING`, `VIX_SPIKE`다.

현재는 로컬 앱 안에서 알림 상태를 분류하고 브라우저 알림 권한이 있을 때만 데스크톱 알림을 띄우는 수준이다. 실제 모바일 푸시 알림은 추후 서버/로그인/PWA 푸시 또는 모바일 앱 전환 때 붙이는 것이 좋다.

## 25. 공개 앱 데이터/로그인 원칙

공개 앱에서는 일반 사용자가 Alpaca API Key를 입력하지 않게 한다. 사용자가 API Key를 직접 넣는 구조는 가입 장벽이 높고, 보안 책임과 데이터 라이선스 설명이 복잡해진다.

운영 원칙:

- 시장 데이터 API 키는 운영자 서버의 `.env`나 호스팅 환경변수에만 저장
- 사용자 앱에는 API Key 입력칸을 노출하지 않음
- 사용자는 관심종목, 보유여부, 평단가, 매수일, 알림 설정만 입력
- 서버가 시장 데이터를 가져오고 신호 계산 결과만 앱에 내려줌
- 데이터 재배포/상업 이용 조건은 실제 출시 전 별도 확인

사용자 `Settings`에서는 API Key 입력칸을 제거했다. 일반 사용자는 키 없이 PulseEdge 분석을 쓰고, 운영자만 서버 `.env`나 호스팅 환경변수에서 시장 데이터 키를 관리한다.

### 25.1 서버 환경변수 샘플 정리

`.env.example`을 서버 운영자용 샘플 파일로 정리했다. 로컬 테스트는 `.env.example`을 `.env`로 복사한 뒤 `APCA_API_KEY_ID`, `APCA_API_SECRET_KEY`만 채우면 된다. 실제 `.env`는 `.gitignore`에 포함되어 코드와 보고서에 키 값이 남지 않게 했다.

서버는 `APCA_API_KEY_ID`, `APCA_API_SECRET_KEY`를 우선 읽고, 호환용으로 `ALPACA_API_KEY_ID`, `ALPACA_API_SECRET_KEY`도 읽는다. CBOE VIX 공식 일봉과 예비 소스인 FRED VIXCLS는 별도 키 없이 가져오므로 `.env`에 넣을 항목이 없다.

앱 안에는 투자 유의 문구를 노출한다. PulseEdge는 투자 판단을 돕는 분석 도구이며, 신호는 수익 보장, 매수/매도 지시, 개인 맞춤 투자자문이 아니다. 가격과 지표는 지연되거나 오류가 있을 수 있으므로 주문 전 차트, 공시, 기업 상황을 사용자가 직접 확인해야 한다.

데이터 기준도 화면에 작게 표시한다. IEX는 단일 거래소 기준이라 전체 미국 시장 체결/거래량과 다를 수 있고, Delayed SIP는 미국 통합 시세 기준이지만 약 15분 지연될 수 있다. VIX는 CBOE 공식 일봉 종가를 우선 사용하고 실패 시 FRED로 전환하며, 실시간 공포지수가 아니다.

Settings에는 접이식 위험 고지를 둔다.

위험 고지 항목:

- 투자 손실: 주식 투자는 원금 손실이 발생할 수 있음
- 신호 한계: 점수와 알림은 과거 가격, 거래량, 지표를 계산한 참고 자료임
- 자문 아님: 사용자의 재산, 투자성향, 목표수익률을 반영한 개인 맞춤 자문이 아님
- 주문 대행 아님: PulseEdge는 매매를 대신 실행하거나 계좌 운용을 맡지 않음
- 알림 한계: 푸시나 로그 알림은 지연, 누락, 중복될 수 있음
- 최종 확인: 실제 주문 전 거래 앱, 공시, 뉴스, 리스크를 사용자가 직접 확인해야 함

첫 실행 때는 투자 유의 동의 화면을 한 번 띄운다. 사용자가 체크박스를 선택하고 `동의 후 시작`을 누르면 브라우저 로컬 저장소에 동의 버전과 시간이 저장된다. 이후 같은 버전에서는 다시 띄우지 않고, Settings의 `동의 다시 보기`에서 내용을 재확인할 수 있다.

출시 전 법/심사 체크포인트:

- 유료 구독으로 종목/매매시점 신호를 제공하면 한국의 유사투자자문업 이슈를 별도로 검토
- 미국 사용자를 대상으로 개인화된 증권 조언과 보상을 결합하면 투자자문 규제 이슈를 별도로 검토
- 앱스토어/플레이스토어 제출 전 금융 서비스, 개인정보, 계정 삭제, 구독 고지 요건 확인
- 마케팅 문구에서 수익 보장, 확정 수익, 무조건 매수/매도 같은 표현 금지
- 백테스트 결과는 미래 성과를 보장하지 않는다는 문구를 보고서와 앱 화면에 유지

### 25.5 분석 속도 개선

관심종목이 늘어나면서 `/api/analyze`가 느려지는 문제가 생겼다. 원인은 신호 계산보다 종목별 시세 데이터를 하나씩 기다리는 시간이 컸다.

반영한 개선:

- 관심종목 분석을 최대 6개 동시 작업으로 병렬 처리한다.
- 같은 종목, 제공자, 피드, 봉, 조회 기간 조합의 주식 바 데이터는 8분 동안 서버 메모리 캐시로 재사용한다.
- 캐시된 바 데이터는 복사본으로 반환해 차트/지표 계산 중 원본 캐시가 오염되지 않게 한다.
- `/api/analyze` 응답에 `elapsed_ms`, `symbols`, `worker_count`를 포함한다.
- 화면의 마지막 업데이트 옆에 `분석 1.2초`처럼 소요 시간을 작게 표시한다.

이 개선은 무료 API 요청량을 줄이고 반복 분석 체감 속도를 올리는 목적이다. 공개 서버로 옮긴 뒤 사용자가 늘어나면 메모리 캐시를 Redis 같은 외부 캐시로 분리하는 것을 검토한다.

### 25.6 게스트 사용자별 저장 구조

로그인 전 단계에서 여러 브라우저의 설정이 섞이지 않도록 게스트 저장 구조를 추가했다.

반영한 구조:

- 브라우저는 `localStorage`에 `pulseedgeClientId`를 만든다.
- 모든 API 요청에는 `X-PulseEdge-Client-Id` 헤더가 붙는다.
- 서버는 이 ID를 사용자 키로 사용해 설정을 분리한다.
- `/api/config`, `/api/analyze`, `/api/backtest`, `/api/data-health`, Alpaca 연결 테스트가 모두 같은 게스트 설정을 기준으로 동작한다.
- 새 게스트 설정이 아직 없으면 현재 `config.json`을 기본값으로 읽는다.
- `user_data/`는 개인 설정 저장소이므로 `.gitignore`에 포함했다.

이 구조는 처음에는 JSON 파일 기반으로 구현됐으며, 25.12에서 SQLite 기반으로 교체했다. 이후 로그인 인증과 계정 삭제를 추가했고, 여러 기기 동기화 검증, 결제, 실제 푸시는 아직 남아 있다.

### 25.8 무료 API 보호/요청량 모니터

운영자 Alpaca 키 하나로 여러 사용자가 데이터를 보는 구조에서는 요청량 관리가 필요하다. 그래서 서버 내부에 간단한 사용량 지표를 추가했다.

반영한 항목:

- 바 데이터 캐시 hit/miss와 적중률 기록
- Alpaca 외부 요청 수, 오류 수, 429 rate limit 횟수 기록
- Alpaca 응답의 rate limit 헤더가 있으면 마지막 값을 저장
- VIX 캐시 hit/miss, CBOE/FRED 외부 요청 수, 오류 수 기록
- VIX 일봉 응답은 서버 메모리에서 1시간 재사용
- `/api/analyze`, `/api/data-health`, `/api/usage`에서 usage 지표 확인 가능
- Settings의 데이터 카드에 `API 보호` 타일 추가
- 자동 새로고침 최소값을 15분으로 제한

이 지표는 정식 모니터링 시스템이 아니라 무료 API 보호용 1차 안전장치다. 공개 사용자가 늘어나면 Redis/DB 기반 요청량 기록, 사용자별 rate limit, 관리자 대시보드가 필요하다.

- `user_settings`: 데이터, 차트, 공포지수, 신호와 알림 설정
- `watchlist_items`: 사용자별 관심종목과 표시 순서
- `positions`: 사용자별 보유종목, 평단가, 수량, 매수일, 손절/목표 기준
- `consent_records`: 향후 로그인 연동용 약관/투자 유의 동의 기록
- 여러 테이블 저장은 하나의 트랜잭션으로 처리해 중간 상태를 남기지 않는다.
- ThreadingHTTPServer 환경을 위해 WAL, foreign key, busy timeout을 적용했다.
- 기존 `user_data/guests/<client_id>.json`은 같은 사용자의 첫 접속 때 자동 이전하고 삭제하지 않는다.
- DB, WAL, SHM 파일은 배포 ZIP과 저장소에서 제외한다.

현재 익명 브라우저 ID는 로그인 인증 수단이 아니다. 계정 인증과 사용자 ID 연결, 계정/데이터 삭제 API는 구현됐고, 공개 출시 전에는 서버 동의 기록의 실제 운영 연결을 점검해야 한다.

로그인은 처음부터 필수는 아니다. 다만 아래 기능을 하려면 사실상 필요하다.

| 기능 | 로그인 필요성 |
| --- | --- |
| 한 기기에서 무료 테스트 | 낮음 |
| 관심종목/보유종목 클라우드 저장 | 높음 |
| 폰/PC 동기화 | 높음 |
| 실제 푸시 알림 | 높음 |
| 유료 구독 | 높음 |
| 계정별 알림 히스토리 | 높음 |

출시 방향은 `게스트/로컬 모드`로 가볍게 시작하고, 클라우드 저장/푸시/유료화 단계에서 로그인을 활용하는 것이다. 계정과 데이터의 직접 삭제는 구현됐으며, 개인정보 처리방침과 고객지원 삭제 요청 절차는 공개 출시 전에 확정한다.

### 25.13 TradingView 상세 차트 전환

공개 화면의 종목 상세 차트를 자체 캔버스에서 TradingView Advanced Chart 위젯으로 전환했다. 기존 Alpaca 연결과 PulseEdge 신호 엔진은 개인용 분석 버전으로 그대로 보존한다.

- Watch/Hold 종목을 누르면 TradingView 차트가 기본으로 열린다.
- TradingView 도구에서 일봉/주봉을 포함한 기간 전환, 확대, 보조지표, 선 긋기를 사용할 수 있다.
- 기본 차트에는 단순 이동평균을 하나 표시하고, RSI·볼린저밴드·일목균형표 등은 위젯의 지표 메뉴에서 선택한다.
- TradingView 출처 링크와 브랜드 표시는 유지한다.
- PulseEdge 진입점수/관리강도, 핵심 지표, 자동 지지·저항, 신호 이유는 차트 아래의 별도 분석 패널에 남긴다.
- TradingView 위젯 데이터나 지표 값을 PulseEdge 계산에 읽어오지 않는다.
- 외부 스크립트가 막히거나 로딩에 실패하면 기존 PulseEdge 캔버스 차트로 자동 전환한다.
- 모바일 390px 폭에서 상세 시트, iframe 폭, 가로 넘침을 점검했고 콘솔 오류가 없음을 확인했다.

중요한 남은 과제: TradingView로 차트를 보여주는 것과 PulseEdge 점수 계산용 원천 데이터를 확보하는 것은 별개다. 공개 출시 전에는 신호 엔진에 사용할 데이터 제공사의 재배포, 파생 데이터, 상업 이용 범위를 확인해야 한다.

### 25.14 선택 로그인 기반

게스트 모드를 없애지 않고 Supabase Auth를 선택적으로 붙일 수 있는 기반을 구현했다.

- 인증 설정이 없으면 기존 브라우저별 게스트 SQLite 저장이 그대로 동작한다.
- 설정 후 이메일 매직 링크와 Google OAuth 로그인을 선택적으로 노출한다.
- 서버는 Supabase 사용자 API로 access token을 검증하고, 토큰 자체는 DB에 저장하지 않는다.
- `auth_identities` 테이블은 외부 인증 사용자와 PulseEdge 계정을 연결한다.
- `guest_account_links` 테이블은 같은 기기의 게스트 데이터가 계정에 반복 병합되는 것을 막는다.
- 첫 로그인 때 관심종목, 보유종목, 설정, 투자 유의 동의를 계정으로 복사한다.
- 다른 기기에서는 기존 계정 설정을 우선하고, 새 관심종목과 보유종목만 한 번 병합한다.
- Settings의 계정 카드는 미설정 상태에서 게스트 안내만 표시하며 로그인 입력칸을 숨긴다.
- Python 테스트는 계정 연결과 병합 테스트를 포함해 51개를 통과했다.

실제 로그인 활성화에는 Supabase 프로젝트 URL과 publishable key가 필요하다. Google 로그인은 Google OAuth 설정과 Redirect URL 등록이 추가로 필요하다.

### 25.15 로그인 우선 시작 화면

공개 앱 흐름을 `앱 진입 후 Settings에서 로그인`에서 `첫 진입 로그인 우선`으로 변경했다.

- 첫 방문에는 PulseEdge 브랜드와 이메일 로그인/회원가입 입력을 먼저 표시한다.
- 이메일 매직 링크는 신규 계정 생성과 기존 계정 로그인을 하나의 흐름으로 처리한다.
- 사용자는 `로그인 없이 둘러보기`를 선택해 게스트 모드로 진입할 수 있고, 선택은 브라우저에 기억된다.
- 로그인 세션이 있으면 재방문 때 시작 화면을 건너뛰며, 로그아웃하면 다시 시작 화면으로 돌아간다.
- 인증 서버가 설정되지 않았거나 모듈 로드에 실패하면 앱을 잠그지 않고 기존 게스트 모드로 안전하게 전환한다.
- Settings의 계정 로그인은 유지해 게스트 사용자가 나중에도 계정으로 전환할 수 있다.
- 서비스 워커 캐시는 `pulseedge-v75`로 갱신했고 Python 53개 테스트와 JavaScript 문법 검사를 통과했다.

### 25.16 계정 및 사용자 데이터 삭제

- 로그인 사용자는 Settings에서 `계정 및 데이터 삭제`를 선택할 수 있다.
- 실수 방지를 위해 현재 로그인 이메일을 정확히 다시 입력해야 영구 삭제가 활성화된다.
- 서버는 access token을 검증하고 서버 전용 `SUPABASE_SECRET_KEY`로 Supabase Auth 계정을 삭제한다. 기존 `SUPABASE_SERVICE_ROLE_KEY`는 호환용으로만 지원한다.
- 이어서 SQLite의 계정, 관심종목, 보유종목, 설정, 동의 기록과 단독 연결된 게스트 데이터를 외래키 연쇄 삭제한다.
- 삭제된 인증 식별자는 표식으로 남겨 만료 전 토큰이나 다른 기기의 오래된 세션이 계정을 다시 만들지 못하게 한다.
- 브라우저의 신호 로그, 차트 설정, 알림 선택, 투자 유의 동의와 게스트 ID도 함께 정리한다.
- service role 키는 서버 `.env`에만 저장하며, 없을 때는 삭제 버튼을 비활성화한다.
- 서비스 워커 캐시는 `pulseedge-v83`으로 갱신했고 Python 72개 테스트와 JavaScript 검사를 통과했다.

## 26. 다음 개선 후보

아래 항목은 바로 구현할 목록이 아니라 백로그다. 앱 화면이 복잡해지지 않는지, 실제로 매일 쓰는 판단에 도움이 되는지 확인한 뒤 하나씩 올린다.

사용자용 웹 API에서 API 키 저장/삭제는 차단했다. DigitalOcean 배포용 환경변수 체크리스트, 서버 실행 구조, 로그인/푸시/클라우드 저장/앱스토어 출시 기준은 `PULSEEDGE_OPERATION_PLAN.md`에 별도 정리했다.

### 26.1 신호 품질 개선 백테스트

현재 방향은 청산 룰을 복잡하게 최적화하기보다, 진입점수 신호 자체가 좋은 종목과 시점을 잘 골라내는지 확인하는 것이다. 우선순위:

1. 여러 종목에서 90일 보유형 기준 신호 품질 검증
2. 최소 진입점수 85/88/90/92 비교
3. 최대 보유 60/90/120거래일 비교
4. 120일선 위 종목만 진입하는 추세 필터 비교
5. 거래량 확인이 붙은 신호와 아닌 신호 비교
6. 시장 리스크온일 때만 진입하는 필터 추가
7. VIX 공포 구간 진입 여부를 별도 비교
8. 수익형/구조손절형은 방어 성향 비교용으로 유지

### 26.2 백테스트 고도화

- 관심종목 전체 일괄 백테스트
- 결과를 종목별/룰별 표로 비교
- 승률보다 평균수익률, 손익비, MDD를 함께 보기
- 표본 수가 적은 결과는 경고 표시
- 수수료/슬리피지 입력
- 기간을 상승장/하락장/횡보장으로 나눠 성능 확인

### 26.3 앱 기능 고도화

- 신호 히스토리 저장
- 관심목록 그룹 만들기
- 알림 읽음/보류 처리
- 보유종목 매수/매도 메모
- 실적 캘린더 API 연결
- 간단한 재무/실적 요약
- 로그인과 클라우드 동기화
- 실제 모바일 푸시
- 앱스토어용 네이티브 앱 또는 Expo/React Native 전환

## 27. 현재 판단

지금 버전은 “신호 앱의 뼈대”는 꽤 잘 잡혔다. 특히 중요한 결정은 세 가지다.

1. Watch와 Hold를 분리해서 같은 종목도 다른 관점으로 본다.
2. 점수는 50점 중립에서 시작해 진입점수와 관리강도를 따로 해석한다.
3. 백테스트는 앱 화면이 아니라 내부 검증과 보고서 기록용으로 둔다.

다음 개발은 기능을 더 많이 붙이기보다, 매일 보기 편한 관심목록과 신호 설명을 다듬는 것이 우선이다. 새 아이디어는 바로 화면에 넣지 않고 백로그에 기록한다. 백테스트는 수익률을 과하게 최적화하기보다 “이 신호가 헛소리가 아닌지” 검증하는 용도로 둔다.
